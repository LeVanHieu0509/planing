## ⚡ CÔNG THỨC PHẢN XẠ DUY NHẤT CHO TOÀN BỘ CUỘC PHỎNG VẤN: `A - R - E`

> 🎯 **Tại sao đưa 100% câu trả lời về chuẩn `A-R-E (Answer – Reason – Example)`?**
> - Khi vào phòng phỏng vấn thật, nếu mỗi câu một kiểu bố cục, não bạn sẽ bị "đứng hình" vì vừa phải nhớ kiến thức Tech, vừa phải dịch tiếng Anh.
> - Khi **mọi câu hỏi đều dùng chung 1 khuôn `A - R - E`**, hễ khách Mỹ vừa dứt lời là não bạn **tự động nhảy số theo đúng 3 nhịp phản xạ**:

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│ 🟢 [A - ANSWER] (Trả lời thẳng trọng tâm trong 1 câu ngắn - Không vòng vo!):             │
│    👉 "Well, [Trả lời trực tiếp cái mình dùng / cách mình làm]..."                       │
│                                                                                          │
│ 🟡 [R - REASON] (Giải thích TẠI SAO / Cơ chế bên dưới bằng từ nối L3):                   │
│    👉 "...because [Lý do kỹ thuật], which means that [Lợi ích / Hệ quả đạt được]."       │
│                                                                                          │
│ 🔵 [E - EXAMPLE] (Chốt hạ bằng 1 Ví dụ thực tế trong 4 dự án CV + Con số kết quả):       │
│    👉 "For example, in my [Tên dự án trong CV], I [Hành động cụ thể], which [Kết quả]."  │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

## 💻 PHẦN 3: TOP 8 CÂU HỎI TECHNICAL CỐT LÕI (100% FORMAT `A - R - E`)

### Nhóm A: Node.js / NestJS / Express.js

#### Q1: Node.js is single-threaded. How does it handle thousands of concurrent requests without blocking?
* 🟢 **[A - Answer]:**
  > *"Well, **under the hood**, Node.js handles high concurrency on a single thread by using an **event-driven, non-blocking I/O architecture** powered by the **Event Loop**."*
* 🟡 **[R - Reason]:**
  > *"Whenever Node hits an I/O operation—like querying PostgreSQL, reading from Redis, or calling an external API—it delegates that work to the OS kernel or worker pool **because** I/O is slow, **which means that** the main thread is immediately free to serve the next user request."*
* 🔵 **[E - Example]:**
  > *"For example, in my projects, I never run heavy CPU loops on the main thread; instead, I use **`async/await`**, **`Promise.all`** for parallel calls, and offload heavy jobs like bulk payment notifications in Project 4 to **Redis background queues** so the Event Loop is never blocked."*

---

#### Q2: You worked with both Express.js and NestJS. What is the difference and when do you prefer NestJS?
* 🟢 **[A - Answer]:**
  > *"From my standpoint, **Express.js** is a lightweight, unopinionated framework great for simple microservices, whereas **NestJS** is a full enterprise framework built on top of Express with strict **TypeScript** and modular architecture."*
* 🟡 **[R - Reason]:**
  > *"For medium-to-large projects, I strongly prefer **NestJS** **because** it provides built-in **Dependency Injection, Modules, Controllers, Guards, Pipes, and Interceptors** (very similar to Java Spring Boot), **which means that** the codebase stays scalable, consistent, and easy to unit test across a large team."*
* 🔵 **[E - Example]:**
  > *"For example, in Project 1 I used Express and Strapi for flexible CMS APIs, but in Project 2 I chose **NestJS** to implement the **Strategy pattern** adapter middleware cleanly using Constructor Dependency Injection."*

---

#### Q3: How do you handle authentication, validation, and global error handling in your APIs?
* 🟢 **[A - Answer]:**
  > *"I handle authentication, validation, and error handling by separating them into dedicated layers along the request pipeline rather than mixing them inside controllers."*
* 🟡 **[R - Reason]:**
  > *"Specifically, I use **JWT Guards / Spring Security Filters** for authentication, **DTO Validation Pipes / `@Valid`** for input checking, and a **Global Exception Filter / `@RestControllerAdvice`** for errors **because** it keeps business logic clean, **which means that** the frontend always receives a consistent JSON response format."*
* 🔵 **[E - Example]:**
  > *"For example, in Project 3’s multi-tenant platform, our global JWT Guard automatically validated the user's token and extracted their `tenant_id` before the request ever reached the controller."*

---

### Nhóm B: Java / Spring Boot & Microservices

#### Q4: Can you explain Dependency Injection (DI) and `@Transactional` in Spring Boot?
* 🟢 **[A - Answer]:**
  > *"In Spring Boot, **Dependency Injection** means the **Spring IoC Container** manages Bean creation and injects dependencies via **Constructor Injection**, while **`@Transactional`** uses a Spring AOP proxy to manage database transactions automatically."*
* 🟡 **[R - Reason]:**
  > *"We use Constructor DI **because** it keeps services loosely coupled and easy to mock in **JUnit and Mockito**, and we use `@Transactional` on multi-step write methods **because** if any `RuntimeException` occurs mid-way, Spring automatically **rolls back** all changes to guarantee ACID data consistency."*
* 🔵 **[E - Example]:**
  > *"For example, in Project 4’s tuition billing service, when a student paid an invoice, I used `@Transactional` to update the invoice status, create a ledger record, and update the student balance atomically—if any step failed, the whole payment transaction rolled back safely."*

---

#### Q5: What is the N+1 query problem in ORM (Hibernate/JPA or TypeORM) and how do you fix it?
* 🟢 **[A - Answer]:**
  > *"The **N+1 query problem** happens when the ORM runs `1` query to fetch a list of `N` parent records, and then unexpectedly runs `N` additional queries inside a loop to lazy-load each parent’s child relationship."*
* 🟡 **[R - Reason]:**
  > *"This is a major database bottleneck **because** fetching 100 items results in 101 separate network round-trips to PostgreSQL, **which means that** API latency spikes dramatically under load."*
* 🔵 **[E - Example]:**
  > *"For example, in Project 4, our financial report had an N+1 issue when loading branch details for hundreds of transactions. I fixed it by replacing the loop with a single **`JOIN` query (`JOIN FETCH` in JPA / `leftJoinAndSelect` in TypeORM)**, cutting the response time from 10 seconds to under 400ms."*

---

#### Q6: How do your microservices communicate? When do you use synchronous vs. asynchronous communication?
* 🟢 **[A - Answer]:**
  > *"In our microservices architecture, we use **synchronous REST APIs** for immediate user-facing requests, and **asynchronous Redis queues** for heavy or background workflows."*
* 🟡 **[R - Reason]:**
  > *"We split them this way **because** synchronous REST calls give instant feedback when the UI needs data right away, whereas async queues decouple services and prevent timeouts **when** a task takes several seconds or depends on slow third-party systems."*
* 🔵 **[E - Example]:**
  > *"For example, in Project 2, user login and viewing course catalogs used synchronous REST APIs, while generating AI course content and syncing with external LMS platforms ran asynchronously through **Redis job queues with automatic 3-time exponential backoff retries**."*

---

### Nhóm C: Database Optimization & AI Tools

#### Q7: What would you do if an API endpoint or database query was running very slowly in production?
* 🟢 **[A - Answer]:**
  > *"If an API endpoint were running slowly in production, **I'd** follow a 3-step method: isolate the bottleneck in logs, analyze the query execution plan with **`EXPLAIN ANALYZE`**, and optimize the indexing, SQL structure, and Redis caching."*
* 🟡 **[R - Reason]:**
  > *"I always run `EXPLAIN ANALYZE` first **because** it shows whether PostgreSQL is doing a costly **full table scan (`Seq Scan`)**, **which means that** we can pinpoint the exact missing index or N+1 query instead of guessing."*
* 🔵 **[E - Example]:**
  > *"For example, in my CRM project (Project 4), a monthly tuition report was taking 10 seconds. After running `EXPLAIN ANALYZE`, I rewrote the N+1 loop into a single `JOIN` + `GROUP BY` query, added a composite index on `(branch_id, payment_date, status)`, and cached the summary in Redis for 5 minutes—dropping load time to under **400ms**."*
